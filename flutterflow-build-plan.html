01 Deploy the API

Upload the /api/ folder to your site root via Hostinger File Manager or FTP, so it resolves at https://snow-jellyfish-553645.hostingersite.com/api/.

Folder layout to upload

config/db.php            ← already exists; the API reuses it
api/
├─ .htaccess             passes the Authorization header through
├─ bootstrap.php         CORS · JSON envelope · PDO · auth (shared)
├─ index.php             GET — lists endpoints (deploy check)
├─ products.php
├─ categories.php
├─ banners.php
├─ pages.php
├─ checkout.php
├─ orders.php
├─ wishlist.php
├─ profile.php

├─ products/   → detail.php · reviews.php · review.php
├─ orders/     → detail.php
├─ wishlist/   → toggle.php
└─ profile/    → update.php
One-time SQL: run the additive CREATE TABLE IF NOT EXISTS api_tokens statement (from the brief) once in phpMyAdmin. It creates the token store and touches nothing else.

The db.php contract

bootstrap.php does require '../config/db.php' and expects a connected PDO handle. It auto-detects a variable named $pdo, $conn, $db, or $dbh — so if your existing file already builds a PDO under any of those names, there is nothing to change. Compare against config.sample.php if unsure (that sample is a reference only — do not upload it).

02 Smoke-test before touching FlutterFlow

Confirm the deploy from a browser and terminal so app-side debugging never chases a server bug.

Open /api/ — you should get the endpoint list wrapped in the standard envelope. Then check a real query and a protected route:

# public — should return products
curl "https://snow-jellyfish-553645.hostingersite.com/api/products.php?per_page=3"

# auth — register, capture the token
curl -X POST https://snow-jellyfish-553645.hostingersite.com/api/auth/login.php \
  -H "Content-Type: application/json" \
  -d '{"login":"you@example.com","password":"secret"}'

# protected — pass the token back
curl https://snow-jellyfish-553645.hostingersite.com/api/profile.php \
  -H "Authorization: Bearer <token-from-login>"

Every response follows one shape — bind to it once and reuse everywhere:

{
  "success": true,
  "data": { /* payload, or null */ },
  "message": "Login successful."
}

03 FlutterFlow: API base + the auth header

In Integrations → API Calls, create one API Group so every call shares a base URL and the token header.

SettingValue
Group nameSoleCraftAPI
Base URLhttps://snow-jellyfish-553645.hostingersite.com/api
Group header 1Content-Type: application/json
Group header 2 (private / optional value)Authorization: Bearer [authToken]
Add Authorization: Bearer [authToken] as a Group-level header whose value is the App State variable authToken. Every call in the group inherits it; public calls simply send an empty bearer, which the API ignores. This is the single most important wiring step — get it right once and every protected screen just works.

Custom Data Type — CartItem

Create under Data Types (App State can't hold ad-hoc objects otherwise):

FieldType

Cart total and cart count don't need stored fields — compute them from cartItems with a simple Custom Function (sum of price × quantity, and list length) so they can never drift out of sync.

Badges & sale price

Each product carries a badge string (New / Sale / Best Seller, or empty) and a boolean on_sale. In the product card:

  • Show a badge pill only when badge is not empty — colour by value (New = ink, Sale = accent/red, Best Seller = amber) to match the site.
  • When on_sale is true, show sale_price as the price and price with a strike-through beside it. Otherwise show price only.
  • Format money as ₱ + value — the store prices in Philippine peso.
Image URLs: the image field is a path stored by the site (e.g. uploads/shoe.jpg). If it doesn't start with http, prefix it with https://snow-jellyfish-553645.hostingersite.com/ before binding it to an Image widget. A one-line Custom Function fullImageUrl(path) keeps this consistent across every screen.

07 The nine screens

Each screen below lists its widgets, the API Calls it fires, the bindings, and the actions. Every API-backed screen uses the same pattern: a loading spinner while the call runs, the content on success, and an error state (message from $.message + a Retry button) on failure.

appState

On page load (actions)

  • If isLoggedIn == true → navigate to Home; else → Login (or an optional onboarding carousel first).

Widgets

  • Centered logo “SoleCraftPH”, tagline “Footwear, Done Right”, subtle progress indicator.

Login / Register

loginUserregisterUser

Widgets

  • Tab or toggle: Sign in / Create account.
  • Sign in: login (username/email), password, “Sign in” button.
  • Register: username, full_name, email, phone, address, password, confirm password.

Actions — Sign in button

  • Validate fields (non-empty, email format, password ≥ 6).
  • Call loginUser. Show spinner; disable button.
  • On success (success == true): set App State authToken = $.data.token, userId, userName, userEmail/Phone/Address, isLoggedIn = true → navigate to Home.
  • On failure: snackbar with $.message (e.g. “Invalid credentials.”).

Actions — Create account

  • Same pattern with registerUser; it also returns a token, so log the user straight in on 201.

Page parameter

Widgets & bindings

Cart

appState only

  • Summary bar: item count + total (Custom Functions over cartItems).
  • “Proceed to checkout” button — disabled when cart is empty.

6

Checkout

checkout

Widgets

  • Shipping form: customer_name, email, phone, address — prefilled from App State when logged in.
  • Payment method picker: COD / GCASH / CARD (maps to the enum).
  • Order summary: line items + total.
  • “Place order” button.

Build the cart payload

The API only needs product_id + quantity (it re-prices server-side, so totals can't be tampered with). Map cartItems → a JSON list:

{
  "customer_name": "[name]", "customer_email": "[email]",
  "customer_phone": "[phone]", "customer_address": "[address]",
  "payment_method": "COD",
  "cart": [ { "product_id": 12, "quantity": 2 } ]
}

Actions — Place order

  • Call checkout (group bearer attaches automatically if logged in).
  • On success (201): read $.data.order_id, clear cartItems, navigate to Order Confirmation showing the id + total.
  • On 409 (out of stock): show $.message and keep the cart so the user can adjust.

08 Recommended build order

Front-load the plumbing so every later screen is just binding to a call that already works.

  • 01  Upload /api/, run the api_tokens SQL, smoke-test with curl (§1–2).
  • 02  Create the SoleCraftAPI group + Authorization: Bearer [authToken] header (§3).
  • 03  Define App State + the CartItem data type (§4).
  • 04  Add all 18 API Calls and test each in FlutterFlow's API test tab (§5).
  • 05  Build Login/Register — the token everything else depends on (screen 2).
  • 06  Build Home → Product Detail with the shared Product Card component (screens 3–4).
  • 07  Build Cart → Checkout → Order Confirmation (screens 5–6).
  • 08  Build Orders, Wishlist, Profile (screens 7–9).
  • 09  Add Splash routing last, once isLoggedIn behaves (screen 1).
  • 10  Pass over loading + error states on every API-backed screen.
Reuse one Product Card component across Home, search results, and Wishlist — build it once with the badge + sale-price logic, and all three screens stay consistent with the live store for free.
