New screens

Seven screens, ordered by how much they hurt to be without. Each names the server work it depends on.

  • Payment ResultS · no new API

    Finishing a GCash payment currently drops the customer onto the website's order_success.php inside the WebView. It works, but it reads like the app handed them off to a browser.

    Needs
    A screen the WebView lands on that says the payment went through and returns to Confirmed. Three ways to get there: point success_url at a slim mobile-styled payment_return.php; or have Confirmed re-poll GetOrder until payment_status flips; or a deep link back into the app.
    Note
    Purely presentational — the webhook already settles the order correctly on its own.
  • Order DetailM · needs API work

    MyOrders lists orders but nothing opens. Tapping an order is the single most obvious missing interaction in the app.

    Shows
    Items with size, quantity and unit price; status timeline from order_status_log; tracking number; payment method and paid/unpaid; delivery address.
    Server
    GET /api/orders.php?id= already returns items and now requires a token. The status timeline is not exposed yet — order_status_history() exists in order_service.php but nothing returns it over the API.
  • NotificationsM · needs new API

    Order-status messages are already written to the notifications table every time an order changes state — including from the app. Customers just can't read them on a phone.

    Shows
    List with unread state, mark-all-read, unread badge on the Account tab.
    Server
    New api/notifications.php — list, unread count, mark read. The service layer (notification_service.php) is done; only the endpoint is missing.
    Later
    Real push (banner when the app is closed) is a separate job: Firebase, a device_tokens table, and a send on status change. This screen is worth having first and works without it.
  • WishlistM · needs new API

    The website has a wishlist in the main nav and a heart on every product. The app has neither, so a customer's saved items vanish when they pick up their phone.

    Shows
    Saved products grid, remove, add-to-bag from the list, plus a heart toggle on ShoeDetails.
    Server
    New api/wishlist.php — list and toggle, bearer-authed. Table and service layer already exist.
  • ProfileM · needs new API

    Account shows a name and a sign-out button. Nothing can be edited, so a customer who moves house has to open the website.

    Shows
    Edit full name, phone, delivery address. Change password with current-password confirmation.
    Server
    New api/profile.php. auth_update_profile(), auth_change_password() and auth_verify_password() all exist already.
    Bonus
    A saved address makes Checkout prefill properly, which is the slowest part of ordering on a phone.
  • ReviewsL · needs new API

    The website shows a star average, a review count and the full list on every product, and lets buyers write one. This is the biggest single content gap between the two.

    Shows
    Rating summary and review list on ShoeDetails; a write-review form for customers who bought the item.
    Server
    New api/reviews.php — list by product, submit. review_service.php exists.
  • Help & InfoS · needs new API

    Contact support and the About / FAQ / Privacy pages. Low glamour, but an app store listing generally expects a privacy policy reachable in-app.

    Shows
    Contact form (name, email, subject, message) and CMS pages by slug.
    Server
    New api/contact.php and api/pages.php. Both services exist; cms_pages already holds about, faq and privacy.

The button problem

You noticed this and it is real. Measured across the generated code:

PropertyDistinct values in use
Button height48 · 50 · 52 · 56 · 64
Corner radius6 · 8 · 10 · 12

Five heights and four radii, chosen ad hoc per screen. Nothing is broken, but taps land on targets of different sizes and corners don't rhyme, which is exactly the "not consistent" feeling.

What to settle on

One primary height (52), one secondary (44), one radius (12), one icon-button size (40). Then a shared Button component with a variant parameter, so a future change is one edit rather than thirteen.

Alongside it: consistent loading, empty and error states. Several screens have none — a failed request currently shows a blank list rather than saying anything went wrong.

Half of this is already written

The api/ folder in your flutter workspace holds unreleased drafts of wishlist.php, contact.php, pages.php, banners.php, profile/update.php, products/reviews.php and products/review.php. None was ever deployed.

They can't be uploaded as-is: they wrap responses in a {success, data, message} envelope, while the live API returns flat JSON and the app's structs are bound to the flat shape. Reworking them is still far less work than writing from scratch — the queries and validation are done.

Suggested order

Sequenced so each step ships something usable, cheapest and most visible first.

  1. Design system passOne button spec, one radius, shared component, loading and empty states. Touches every screen, so doing it first stops the new screens from adding to the inconsistency.
  2. Payment Result + Bag quantityTwo small fixes closing the two roughest edges in a flow customers already use.
  3. Order DetailThe clearest missing interaction. Needs the status timeline exposed over the API.
  4. Profile + Account entriesUnblocks address editing, which makes checkout faster.
  5. NotificationsThe data is already being written on every order change; only the endpoint and screen are missing.
  6. WishlistCross-device saving, same shape as the cart sync already built.
  7. ReviewsLargest content gap and the largest job — worth doing once everything around it is stable.
  8. Help & InfoContact and CMS pages. Small, and a privacy policy is usually expected for a store listing.
